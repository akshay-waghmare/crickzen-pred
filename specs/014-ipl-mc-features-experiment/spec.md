# Feature Specification: IPL MC Features Experiment

**Feature Branch**: `014-ipl-mc-features-experiment`  
**Created**: 2026-04-27  
**Status**: Draft  
**Input**: Test whether adding calibrated Monte Carlo outputs and MC-vs-resource disagreement features to the IPL ML training set can improve Brier score, ECE, and log loss versus the current IPL v6 model.

## Definitions

- **Current IPL baseline**: The existing IPL model family using `models/ipl_v6` and feature data in `data/ipl_features_v6/training.parquet`.
- **resource_win_prob**: Existing resource-based probability generated by feature engineering. It is already part of `XGBLogRegEnsemble.TOP_FEATURES`.
- **MC raw win probability**: The raw mean probability returned by the Monte Carlo simulation for a historical ball state, before post-hoc calibration.
- **mc_win_prob**: Fold-local calibrated MC probability. During evaluation, its calibrator must be fitted only on the training fold, then applied to validation/test rows.
- **MC uncertainty**: The simulation standard deviation for the same MC run, stored as `mc_simulation_std`.
- **MC-resource disagreement**: Directional and absolute gaps between MC and resource probability:
  - `mc_resource_gap = mc_win_prob - resource_win_prob`
  - `mc_resource_abs_gap = abs(mc_win_prob - resource_win_prob)`
- **Experiment artefact**: Any generated cache, metric table, report, or model created for this experiment under `experiments/ipl_mc_features_v1/`. These artefacts are not production models.

## Current State

### What Already Exists

- `data/ipl_features_v6/training.parquet` and `training_sampled.parquet` exist.
- `models/ipl_v6/champion_model.joblib`, `oof_calibrators.pkl`, `OOF_CALIBRATION_REPORT.md`, and `oof_calibration_results.csv` exist.
- The training model class `XGBLogRegEnsemble` already includes `resource_win_prob` in its selected top features.
- The MC simulation engine returns probability distributions with a mean and standard deviation.
- `scripts/analyze_mc_cal_as_feature.py` already tests a related idea on T20I male data: original resource probability, calibrated MC replacement, and both features.
- `bbl-pipeline calibrate-mc` and `bbl_pipeline.calibration.mc_trainer` already support training MC Platt calibrators from match JSON.

### What Is Missing

- No IPL-specific experiment script exists that compares IPL v6 baseline against MC-augmented IPL feature variants.
- The current `XGBLogRegEnsemble.TOP_FEATURES` does not include `mc_win_prob`, `mc_resource_gap`, `mc_resource_abs_gap`, or `mc_simulation_std`, so simply adding columns will not make the model use them.
- A leak-free fold-local MC calibration workflow does not yet exist for this IPL feature experiment.
- Historical MC feature cache does not exist for IPL v6 training rows.
- Live inference does not yet compute MC-derived features before ML prediction, so any production promotion would require a latency-aware inference change.

## User Scenarios and Testing

### User Story 1 - Offline IPL Metric Improvement Experiment (Priority: P1)

As a model developer, I want to run a leak-free IPL experiment that compares the current IPL ML model against ML variants using calibrated MC features, so that I can determine whether MC outputs improve Brier score, ECE, and log loss before touching production.

**Why this priority**: This is the core hypothesis. Without a rigorous offline comparison, adding MC-derived features risks overfitting, leakage, or a slower model with no real quality gain.

**Independent Test**: Run one command that produces `experiments/ipl_mc_features_v1/REPORT.md` and `metrics.csv`, with rows for baseline and each MC feature variant. The report must show Brier, ECE, and log loss overall, by innings, and by phase.

**Acceptance Scenarios**:

1. **Given** the IPL v6 training data exists, **When** the experiment script is run in pilot mode, **Then** it produces a metrics table comparing baseline ML, MC standalone, and MC-augmented ML variants on the same IPL rows.
2. **Given** the experiment uses calibrated `mc_win_prob`, **When** cross-validation runs, **Then** each validation fold receives MC calibration fitted only on that fold's training rows.
3. **Given** a candidate variant improves Brier but worsens log loss or ECE, **When** the final report is generated, **Then** the result is marked "do not promote" unless all promotion gates pass.
4. **Given** the experiment completes, **When** `metrics.csv` is inspected, **Then** it includes at minimum `method`, `split`, `segment`, `n`, `brier`, `ece`, `log_loss`, and delta columns versus the baseline.

---

### User Story 2 - Historical MC Feature Cache (Priority: P1)

As a model developer, I want a reproducible cache of MC-derived features for IPL historical ball states, so that experiments do not need to rerun expensive simulations every time.

**Why this priority**: MC simulation is the expensive part. A cache makes the experiment repeatable, auditable, and fast enough to iterate.

**Independent Test**: Generate `experiments/ipl_mc_features_v1/mc_feature_cache.parquet` and verify every cached row can join back to the IPL feature row without changing row order or labels.

**Acceptance Scenarios**:

1. **Given** `data/ipl_features_v6/training_sampled.parquet` is used for a pilot, **When** the cache generator runs, **Then** it writes MC features for every selected row or clearly records rows skipped with reasons.
2. **Given** `data/ipl_features_v6/training.parquet` is used for a full run, **When** the cache generator resumes after interruption, **Then** it reuses completed rows and continues without duplicating row keys.
3. **Given** the same seed, row keys, and simulation settings, **When** the cache is regenerated, **Then** aggregate MC metrics are reproducible within expected simulation noise.
4. **Given** a row has invalid state for MC simulation, **When** it is processed, **Then** the row is excluded from experiment training and reported in `cache_quality.json`.

---

### User Story 3 - Safe Promotion Path to IPL v7 (Priority: P2)

As a model owner, I want a clear go/no-go rule for turning a successful experiment into an IPL v7 production model, so that production is not changed based on a noisy offline result.

**Why this priority**: MC features introduce inference latency and dependency complexity. A promotion path is needed, but only after proof.

**Independent Test**: If a candidate passes all metric gates, create a non-active candidate directory `models/ipl_v7_mc_features_candidate/` and verify it can score a recorded live state only when MC features are available.

**Acceptance Scenarios**:

1. **Given** an MC-augmented candidate passes all offline gates, **When** a candidate model is trained on all IPL v6 rows, **Then** it is saved under a candidate path and is not registered as the active IPL model.
2. **Given** the candidate requires MC features, **When** live inference is tested, **Then** the predictor computes resource features first, runs independent MC simulation, appends MC fields, and then calls the ML model.
3. **Given** live inference latency exceeds the configured update budget, **When** promotion is evaluated, **Then** the candidate is rejected or marked "offline-only" regardless of offline metric gains.
4. **Given** the candidate passes offline and latency gates, **When** it is considered for production, **Then** IPL v6 remains the active model until a side-by-side live dry run is completed.

## Edge Cases

- **MC calibration leakage**: Existing full-data calibrators must not be used inside validation folds. Calibrators must be trained inside each fold.
- **Circular dependency**: MC features used by ML must be generated using an independent MC evaluator, not the same candidate ML model. Otherwise prediction depends on itself.
- **Simulation noise**: Small metric gains may be random. The experiment must use fixed seeds and enough simulations to make deltas stable.
- **Rows with terminal or near-terminal states**: Rows with zero balls remaining, impossible target state, or already-completed chase must be handled consistently and reported.
- **Missing state columns**: If IPL v6 feature rows cannot be mapped to `MatchState`, the cache generator must fail with an actionable missing-column report.
- **Feature selection blind spot**: Because `XGBLogRegEnsemble` uses a fixed top-feature list, MC experiment variants must explicitly include MC feature names in the candidate feature list.
- **Latency regression**: Even if metrics improve, adding MC before ML may be too slow for live dashboard updates unless n-simulations, caching, or async execution is controlled.

## Requirements

### Functional Requirements

- **FR-001**: The experiment MUST generate the following MC feature columns: `mc_raw_win_prob`, `mc_win_prob`, `mc_resource_gap`, `mc_resource_abs_gap`, and `mc_simulation_std`.
- **FR-002**: The experiment MUST preserve the existing baseline feature set and train a baseline model under the same split/evaluation protocol used by MC variants.
- **FR-003**: The experiment MUST compare at least these methods:
  - `baseline_ipl_v6_features`
  - `mc_standalone_calibrated`
  - `ml_add_mc_win_prob`
  - `ml_add_mc_gap_features`
  - `ml_replace_resource_with_mc`
- **FR-004**: MC calibration for `mc_win_prob` MUST be fitted inside each training fold only and applied to validation/test rows without seeing their labels.
- **FR-005**: The experiment MUST report Brier score, ECE, and log loss overall, by innings, and by phase.
- **FR-006**: The experiment MUST output `experiments/ipl_mc_features_v1/metrics.csv`, `feature_importance.csv`, `cache_quality.json`, and `REPORT.md`.
- **FR-007**: The experiment MUST not overwrite `models/ipl_v6`, `data/ipl_features_v6`, or the active IPL registry entry.
- **FR-008**: The MC cache MUST include enough metadata to reproduce it: source data path, row key columns, seed, n-simulations, horizon, model/evaluator mode, created timestamp, and git status summary when available.
- **FR-009**: The experiment MUST explicitly extend the model feature list for candidate variants so MC columns are actually trainable.
- **FR-010**: Any production promotion MUST be separated from the experiment and must create a candidate model directory first.

### Non-Functional Requirements

- **NFR-001**: Pilot mode should complete on `training_sampled.parquet` within a practical local iteration window.
- **NFR-002**: Full mode must support resume from an existing MC feature cache.
- **NFR-003**: Metric output must be deterministic except for documented Monte Carlo simulation noise controlled by seed and simulation count.
- **NFR-004**: Live candidate inference must document expected added latency and must fail gracefully if MC features cannot be computed.

## Key Entities

- **IPL MC Feature Cache**: A Parquet table under `experiments/ipl_mc_features_v1/` keyed to IPL training rows and containing raw MC probability, calibrated MC probability where applicable, MC uncertainty, and join metadata.
- **MC Calibrator**: A fold-local Platt or isotonic calibrator mapping raw MC probability to calibrated `mc_win_prob`.
- **Experiment Variant**: A named model configuration with a specific feature set and treatment of `resource_win_prob`.
- **Experiment Report**: Markdown report summarizing overall and segmented metrics, metric deltas, feature importance, cache quality, and go/no-go recommendation.
- **IPL v7 Candidate**: Optional non-active model artefact generated only if promotion gates pass.

---

## Success Criteria

- **SC-001**: Pilot experiment completes and writes all required artefacts under `experiments/ipl_mc_features_v1/`.
- **SC-002**: Full experiment uses a leak-free split protocol and produces `metrics.csv` with baseline and all required MC variants.
- **SC-003**: A candidate is considered successful only if it improves baseline Brier by at least 0.001 absolute on OOF or time holdout and does not worsen log loss or ECE.
- **SC-004**: The winning candidate must not worsen Brier by more than 0.003 absolute in either innings or any major phase segment.
- **SC-005**: If metric gains are below threshold, the report must recommend no production model change and preserve IPL v6 as active.
- **SC-006**: If a candidate passes offline gates, a latency check must demonstrate live inference remains within the dashboard update budget before any production promotion.

---

## Assumptions

- IPL v6 feature rows contain enough state columns to reconstruct MC `MatchState`; if not, the experiment will add a row reconstruction step from raw IPL Parquet/JSON.
- The initial experiment uses standard 20-over IPL matches only.
- MC features are generated from current state only. Actual match outcome is used only for calibrator fitting and metric calculation.
- The first pass should prioritize correctness over speed; optimization comes after a positive signal.
- Promotion, registry updates, and dashboard defaults are out of scope until the experiment report recommends promotion.
